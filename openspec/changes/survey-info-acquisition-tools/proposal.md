# Proposal

## Why

开发期构造器变更在提案、设计与任务中形成或新增信息需求清单时，需要核对哪些工具及组合能在目标语言、平台和环境中提供所需原始信息，避免以现成工具反推事实需求。已有[工具调研报告](research/semantic-tooling-survey.md)是可供增量复核的材料；本变更按[主变更](../epic-layered-semantic-fact-skill/proposal.md)确定的职责边界持续补充研究依据，不重新研究四层事实目录。

## What Changes

- 以开发期构造器变更提案、设计与任务交付的信息需求清单及其新增需求为触发与输入，复核已有报告，按需求增量补充候选工具、覆盖、限制和证据；不把已有报告直接视为对新需求及所有环境均有效的结论。
- 为候选记录可提供的信息、语言与平台环境适用性、调用剖面、输出形态、轻量程度及组合说明；保留适用环境不同的候选，一个需求允许由多个工具组合覆盖，不要求单工具全覆盖。
- 先满足信息需求与环境约束，再优先轻量、简单和多语言支持；不得全局只保留最轻工具或多语言工具，也不在报告中代替构造器完成运行时选型。
- 汇总尚未覆盖的信息与需解析转换的输出，作为解析器开发的需求依据；研究结论通过矩阵维护接口补充工具说明，新增条目保持未点亮。研究、新工具接入与构造器均不能点亮条目，只有解析器开发流程验收完成后可经更新接口点亮，表示对应工具已验收、可供构造器调用。
- AI 归纳与工具输出解析分别表达：现有来源证据可供构造器受约束归纳，不将认知归纳伪装为工具解析，也不以解析器点亮门禁阻断全部认知需求。
- 研究依据继续落在本变更的 `research/semantic-tooling-survey.md`；本轮仅修订规划文档，不改写该报告。

- 信息需求清单是构造器变更的开发期设计与任务交付；工具研究、解析器开发及验收点亮均在开发期完成。运行时构造器只消费既定清单与已点亮矩阵，不生成开发期需求清单，不启动研究、解析器开发或点亮。

## Capabilities

### New Capabilities

无。本变更仅产出调研文档，保持 `skip_specs: true`，不新增系统行为规范。

### Modified Capabilities

无。

## Impact

- 主变更拥有总设计、公共契约、依赖编排和集成验收；本子变更仅负责按需工具研究及其依据。
- 为矩阵维护与解析器开发提供研究输入，工具执行和运行时组合选择属于构造器，解析转换属于解析器。
- 本轮不修改产品、公共 schema 或研究报告，不创建 design/tasks，不实施或归档。

## 项目分析类 Skill 调研范围（明确约束）

- 本变更除程序工具外，只调研**独立项目分析类 Skill**：即自身具有项目级代码理解/分析任务、明确输入输出与可调用入口，能够针对代码库产出分析结果的 Skill。
- 不调研通用 AI 代理/模型宿主、代理运行平台、模型服务或“如何选择 AI 代理”。当工具与独立项目分析类 Skill 均不能满足剩余需求时，AI 兜底直接使用该 Skill 的既定宿主；宿主是运行依赖，不是本次候选调研对象。
- 不把普通 prompt、角色设定、单个工具的薄封装或仅对已有结果做措辞润色的 Skill 当作独立项目分析类 Skill。若某 Skill 主要编排多个工具，须记录其独立编排/语义分析增量，避免重复计算底层工具覆盖。
- 以固定 `information-needs.json` 的需求为评估依据，记录 Skill 的真实入口、输入/输出、支持语言、项目范围、可用证据与定位、依赖工具、权限/数据边界、失败行为及逐项覆盖。公开说明只能作为候选发现依据；能力结论须标明文档证据、可执行验证证据和未验证项。
- 调研报告只形成候选与覆盖评估，不调用生产构造器、不更改能力矩阵启用状态，也不声称 Skill 已接入运行时。接入、调度与端到端验收由后续对应 OpenSpec 变更负责。

## 语言范围与混合语言项目（明确约束）

- Python/Rust 是当前产品第一阶段已实现的解析器与生产链范围，不是独立项目分析类 Skill 的调研准入限制，也不是最终产品语言边界。
- 独立项目分析类 Skill 应按语言无关的项目分析能力评估，优先验证其对混合语言项目的整体建模能力：识别各语言/构建生态、跨语言项目边界、跨语言调用/接口/数据交互、共享组件、依赖方向和各语言证据的来源归属。
- 候选可只支持部分语言；必须如实记录支持语言及跨语言盲区。只有在目标混合项目中真实验证过的能力，才能标为混合语言已验证；分别通过 Python 与 Rust 单语言夹具，不足以证明跨语言分析能力。
- 调研报告应将“当前实现已支持的语言”“Skill 自身支持的语言”“Skill 对混合语言项目的已验证能力”分开记录。不得因当前解析器只支持 Python/Rust 而把 Skill 候选限制为这两种语言，也不得把调研结论直接视为运行时已实现的多语言支持。
## 候选优先级：工具驱动、结构化输出与低 Token 消耗

- 项目分析类 Skill 的候选排序优先考虑：先运行本地/确定性工具生成结构化 JSON 或图数据，再由 AI 查询局部结果；尽量避免让模型逐文件阅读源码或反复复述整库内容。
- 优先级指标依次为：①实际工具/脚本驱动而非纯提示词阅读；②结构化、可查询、可重复使用的机器输出；③代码分析路径的 LLM token 消耗可为零或显著低于逐文件推理；④语言覆盖与混合语言关系能力；⑤证据定位、来源状态和未知/冲突处理；⑥运行成本、安全与宿主兼容性。
- Token 节省必须由实际运行日志/调用统计验证，不能仅引用项目宣传。应区分代码结构分析的 token 消耗与文档/语义总结阶段的消耗，也要统计模型为读取 Skill 本身和查询图结果所花的 token。
- 调研应优先实测脚本驱动且输出结构化图的候选（例如 CodeGraph Explorer），再与 Understand Anything、Graphify 等候选比较；此排序是调研优先级，不是提前选定生产方案。
## 工具能力重叠与 Skill 增量价值判定

- 调研独立项目分析类 Skill 时，必须把“Skill 是否通过工具实施分析”作为首要分类维度，而不是仅按结构化输出或 Token 成本排序。
- 若 Skill 主要按固定顺序调用现有工具，且输出信息、证据定位、覆盖范围和完整性与直接调用工具相同，则优先采用现有工具组合，不将该 Skill 作为第二级生产者接入；只记录其流程参考价值。
- 若 Skill 能组合多个不同工具、根据结果自适应选择后续工具、补齐跨文件/跨语言关系、保留独立证据/冲突，或产生现有工具无法直接获得且可验证的语义分析结果，则评估其增量价值。Skill 的价值必须通过与直接工具基线的对照实验证明，不能由说明文档或自然语言总结的丰富程度推断。
- 候选实验必须记录底层工具调用清单、每个工具的原始输出、Skill 新增的输出/推导、覆盖差异、错误/遗漏差异、Token 成本和运行耗时。相同底层输出不得在工具与 Skill 两处重复计为覆盖。
- 优先级采用两阶段门槛：先证明 Skill 相对现有工具组合有可验证的能力增量，再比较 Token 成本与运行成本。没有增量的 Skill 即使结构化输出更漂亮或成本较低，也不应优先接入；增量明确后再优先选择低 Token、可查询的结构化输出。
- AI 兜底仍使用选定项目分析 Skill 的既定宿主，但宿主不属于本次调研对象。若工具已能满足需求，不因存在 Skill 就额外调用 Skill；若工具与 Skill 都不能充分满足需求，才由该宿主中的 AI 基于已有证据推导并保留未知/缺口。
## Skill 自动安装准备度（调研职责）

- 候选评估必须记录规范来源、许可、版本固定策略、宿主官方安装机制、依赖/构建要求、可调用入口、安装后验证命令、所需权限、文件写入、网络/数据外发、项目代码执行、hooks/后台行为及卸载/回滚方式。
- 优先考虑可复现、可隔离、可验证且不需要广泛权限的 Skill，但安装容易程度不能替代前述工具增量价值和混合语言质量门槛。
- 本调研不自动安装、授权或启用候选。运行时若选中已验收 Skill 且宿主支持已获准安装机制，自动安装由构造器/宿主适配器负责；否则向用户提供准确安装步骤并继续独立工作。调研只提供这些步骤和安全前提，不负责运行时安装。
