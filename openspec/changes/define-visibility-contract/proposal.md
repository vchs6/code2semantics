# Proposal：语言无关的成员可见性契约

## Why

不同编程语言的访问修饰符不仅名称和取值不同，即使名称相同，其可访问边界和默认规则也可能不同。例如，C#、Kotlin 与 Swift 的 `internal` 并不表达完全相同的访问范围。若将成员可见性建模为固定的跨语言枚举，会丢失源语言语义；若将所有差异塞入语言专属的主体字段，又会使多层语义事实模型难以扩展。

需要为语言无关的多层语义事实模型明确一种可扩展的可见性表达方向，在保留源语言信息的同时，以结构化属性表达访问约束，而不把尚未确认的可访问性推断成事实。

## What Changes

- 保留统一的 `visibility` 属性，但其值采用结构化的 `VisibilityContract`，而不是固定的跨语言可见性枚举。
- 契约应支持保留源语言访问声明及显式声明状态，并允许根据语言规则表达隐式默认值；不得将源代码原始声明与默认规则推导出的结果混为一谈。
- `access_policy` 采用开放的 Key-Value 对表达访问边界和约束。键和值应具有明确语义，并允许不同语言保留真实差异；不采用 `ATOM`、`AND`、`OR` 等条件表达式 AST，也不要求所有语言使用相同的键或值。
- `declared.explicit` 为可选 Boolean：`true` 表示确认源代码显式声明访问修饰符；`false` 表示确认源代码未显式声明访问修饰符；字段缺失表示该状态未知或未记录。不得将字段缺失自动补为 `false`。
- 允许 `visibility: {}`，表示当前未记录具体可见性声明或约束。空对象不代表 `public`、`private` 或任何其他具体访问权限，也不要求为填满结构而推断语言默认规则。
- 可见性契约应保留原语言的访问边界和默认规则，并允许未来增加新的访问策略属性，而不要求修改语义事实模型的主体结构。
- 本提案只确立问题范围、设计方向与关键约束。具体字段契约、语言映射、校验规则、组件职责、验收场景和实现任务，须在提案审查确认后再进入设计与任务分解阶段。

## Capabilities

### New Capabilities

- 语言无关的成员可见性契约：为语义实体提供保真、可扩展的结构化可见性表达方式。

### Modified Capabilities

暂不指定。应在本提案审查确认后，再确定需要影响的现有能力及其归属。

## Impact

- 预期影响语言无关语义事实模型中成员可见性属性的公共表达方式，以及后续使用该属性的构造器、仓库和查询消费者。
- 本阶段仅建立独立提案，不修改主提案、其他组件提案、设计文件、规范文件、任务分解、代码或现有公共契约。
- 提案获确认后，再根据现有 OpenSpec 变更的职责边界确定设计归属与依赖关系；不得因为存在跨组件影响，就默认由主提案承载全部细节。
