# Design

## Context

现状（均已核实落盘）：构造器变更（`add-semantic-fact-constructor`）已定稿 proposal/specs/design/tasks——其 design 决策 5 确立“能力矩阵只读、解析器只调用”，决策 6 确立执行器由矩阵条目声明的调用剖面（命令/超时/重试/输出类型→解析器映射）驱动，Open Question 4 声明调用剖面字段结构随本变更 schema 定稿回填。生产能力调研（`survey-info-acquisition-tools`）在途（0/6），其 tasks.md 第 5 条已固化报告结构：覆盖矩阵逐格“可完成/部分可完成/不可完成”判定及一行证据，第 6 条固化差距清单。解析器变更（`add-info-parser`）仅脚手架，提案内容未写。

依据产物（config design 规则：只固化有产物支撑的结论，逐条引用）：

- 本变更定稿 proposal：矩阵定位、主要提供、职责边界、核心设计原则。
- 构造器 design（`../add-semantic-fact-constructor/design.md`）：决策 5（只读消费）、决策 6（调用剖面字段构成）、Open Question 4（字段结构待本变更回填）。
- 调研 tasks（`../survey-info-acquisition-tools/tasks.md`）：第 5 条（判定等级三档 + 逐格证据）、第 2/3 条（生产者三类：宿主工具/项目分析 Skill/智能体形态）、第 6 条（差距清单结构）。
- AGENTS.md 原则 7 与 config rules.design：确定性实现优先。

## Goals / Non-Goals

**Goals:**

- 固化矩阵条目 schema 的字段集合与维度（信息需求 × 生产者），含运行平台与运行指导。
- 固化播种/更新/一致性校验脚本的实现形态与验证方式（确定性程序）。
- 固化存储形态与只读查询接口形态，使构造器可稳定消费。

**Non-Goals:**

- 不生产矩阵内容（播种来自调研报告，点亮来自解析器落地）。
- 不实现解析器、不决定补建哪些解析器（属 `add-info-parser` 及其门禁）。
- 不做事实构造、不修改调研报告结构。

## Decisions

1. **条目维度与字段集合**：条目 = 信息需求 × 生产者的交叉格；字段为判定等级（可完成/部分可完成/不可完成）、生产层级（工具直出/项目分析 Skill/智能体兜底）、运行平台、运行指导、调用剖面（命令/超时/重试/输出类型→解析器映射）、证据引用（指向调研报告位置）、状态（未点亮/已点亮）。判定等级三档与逐格证据沿用调研 tasks 第 5 条；生产层级三分类沿用调研 tasks 第 2/3 条的生产者分类；调用剖面字段构成沿用构造器 design 决策 6；运行平台与运行指导为本 proposal「主要提供」1/6 声明的维度。字段命名、必选性与枚举值细节在实现任务中定稿（Open Question 2/3 保留部分细化项）。
2. **判定与平台分离**：判定等级表达“该生产者能否产出该信息”的能力判定，运行平台表达“在何 OS 上可运行”的环境约束——两者正交，一个条目可声明多平台；构造器按“判定可完成 且 解析器已实现 且 平台匹配”筛选。备选（判定内嵌平台因素）被否——会把环境约束混入能力判定，跨平台复用时判定失真。依据：proposal「主要提供」1/6。
3. **存储形态：版本化结构化文件（YAML 多文件），随仓库提交**：矩阵需 diff 评审与演进追踪（proposal「主要提供」2），数据量为条目级小规模，单写者场景无并发问题；文件形态使 git diff/评审/回滚直接可用。备选（SQLite 数据库）被否——无并发与关系查询需求，SFRS 的嵌入库判词在此不成立（矩阵无事务与多实体关联查询需求）；备选（独立于仓库的位置）被否——脱离 git 即失去版本化与评审通道。依据：proposal「主要提供」2、proposal「核心设计原则」4。
4. **播种/更新/校验均为确定性 Python 脚本 + pytest 验证**（规则 7）：播种（报告→条目）是确定性转换，同报告必同结果；更新（点亮/增补）是确定性登记；校验（回链/孤儿/自洽）是确定性检查。均实现为程序，MUST NOT 由代理按文档描述手工维护矩阵。schema 为唯一校验依据（JSON Schema）。依据：AGENTS.md 原则 7、config rules.design、proposal「核心设计原则」2、spec「矩阵只记现状且内容外源」。
5. **只读查询接口为同进程库调用**：构造器经程序内接口（读文件 + 查询函数）消费矩阵，非网络服务。依据：单机单消费方（构造器），与 SFRS design 决策 8“宿主本地组件”判词同构；备选（网络查询服务）被否——无第二消费方，前置复杂度无支撑。依据：proposal「主要提供」6、构造器 design 决策 5。
6. **矩阵不代决策、内容外源（现状 as-is）**：矩阵只承载现状与差距记录，立项决策属解析器提案门禁（既有共识：仅明确指示时复评、有新工具需求才启动）；内容唯一来源为调研报告与解析器落地，播种/更新是仅有的两条写入通道。依据：proposal「职责边界」、spec「矩阵只记现状且内容外源」、既有共识“解析器提案有短路退出条件”。

## Risks / Trade-offs

- [调研报告未落盘，播种脚本验收缺乏真实输入] → 用样例报告 fixture 验证转换逻辑；真实报告落盘后执行一次真实播种作为集成验证（tasks Workflow follow-up）。
- [schema 字段与调研实际发现的能力形态不匹配] → schema 版本化；校验对未知字段报错而非静默丢弃，重大不匹配回溯本变更评审，不静默扩字段。
- [矩阵与报告双份内容漂移] → 播种为唯一转换通道，条目证据必须回链报告，一致性校验检出无回链条目；构造器只读矩阵、不读报告，单一事实源唯一。
- [信息需求清单尚未落盘，矩阵行维度标识无对接基准] → 行维度标识与构造器信息需求清单对齐（构造器 design OQ1），对齐前骨架用占位标识并显式标注；清单落盘后统一替换（Workflow follow-up）。

## Migration Plan

纯新增：schema、脚本、空矩阵骨架均为新增文件，不改既有文件；回滚 = 删除新增文件，无数据迁移。矩阵落盘目录与文件布局在实现首任务中确定并创建骨架（随仓库提交，见决策 3）。

## Open Questions

1. **行维度标识规范**：矩阵条目中“信息需求”的标识格式与粒度，须与构造器信息需求清单（`add-semantic-fact-constructor` design OQ1）对齐；清单落盘后回填。
2. **生产层级词汇表**：三层分类（工具直出/分析 Skill/智能体兜底）的最终枚举与是否细分，待生产能力调研回填（fact-catalog「待回填项」的生产方式结论）。
3. **调用剖面字段结构**：命令/超时/重试/输出类型→解析器映射的字段命名与结构，与解析器注册接口协议（`add-info-parser` 设计产出）对齐后回填；回填前骨架中以占位结构标注。
