# Tasks

> 阶段顺序：契约机读 schema 固化 → 结构化模型定义 → 有限调研回填 design Open Questions → 实现 → 验证。机读 schema 忠实转写既有契约文档，不修改契约语义；fact-catalog 生产方式回填属 survey-info-acquisition-tools，本清单不涉及。每项实现任务的验证直接引用 spec 场景；契约参考文件如因生产能力调研发生结构变化，任务 1.1 的前置核对先行拦截。

## 1. 契约机读 schema 固化（语言无关权威）

- [x] 1.1 前置核对：确认 `skills/layered-semantic-facts/references/` 下 contract-format.md、output-schema.md、fact-catalog.md 现文与 epic 归档状态一致、无未处理变更；如有结构变化，停下按 proposal 边界约定另行提案。验证：核对结论记录在变更目录
- [x] 1.2 以三份契约文档为唯一语义来源，编写机读 schema（JSON Schema，落盘路径由任务 3 调研结论确定后落盘并回填此处路径）：语义事实集与语义实体、属性、关系的结构，层级归属元数据，证据定位（文件:行号范围），来源记录，项目版本字段。验证：JSON Schema 语法有效（可用标准校验器解析），逐节对照三份文档无遗漏、无文档外新增内容
- [x] 1.3 准备正反样例数据各至少一份（结构合规的事实集/实体/关系；不合规条目、无效引用、语义报告各一），作为阶段 4 校验与阶段 5 验证的固定测试资产。验证：样例落盘，合规样例通过 schema 校验、各类不合规样例均被拒且失败原因可定位

## 2. 结构化模型定义（读写单位契约）

- [x] 2.1 以机读 schema 与 fact-catalog 词汇为依据，定义语义实体记录模型：稳定标识（Skill 提取流程提供，跨项目版本追踪同一实体，见 design 决策 5/7）、属性、显式关系、层级归属元数据（来自事实清单四层，见 design 决策 6）、来源/证据字段。验证：模型能表达 spec「语义事实集为读写单位」「按范围精确查询与关系遍历」的全部场景，四层视图可由元数据重建
- [x] 2.2 定义读写单位契约的操作语义：事实集提交（原子生效）、单实体/关系增量更新、批量提交、失效、幂等规则（同 ID 同内容幂等、同 ID 不同内容判版本冲突拒绝）、按（项目、版本）读取。验证：契约操作覆盖 spec「增量维护与幂等写入」「事实不可变与按版本追溯」「版本由调用方给定」全部场景，语义报告在契约层即被判为非法输入
- [x] 2.3 以机读 schema 为唯一依据派生 SQLite DDL 与 Python 数据结构绑定：表结构（实体/关系/来源记录，决策 7 实体粒度）、（项目、版本）字段、约束（同 ID 同版本内容唯一）。验证：DDL 可在 SQLite 中建库执行，绑定可装载 1.3 合规样例；DDL/绑定与 schema 逐字段对照无漂移，schema 变更时可再生成

## 3. 仓库设计调研（有限调研，一次成稿）

- [x] 3.1 针对 design Open Questions 1–4（SQLite 表级布局与索引、实体稳定标识机制、版本保留策略与未指明版本语义、数据库文件落盘位置）开展有限调研：每事实≤2 个二手源、止损记差距，产出调研纪要落盘至变更目录 `research/repository-design-survey.md`。验证：四个问题各有结论或显式差距记录，无超过 2 源的事实条目
- [x] 3.2 依据调研纪要回填 design.md Open Questions：逐项固化决策并引用纪要对应章节；未决项采用最保守可选方案并显式标注（实体标识红线不因调研放宽：身份判定责任留 Skill 提取流程）。验证：design.md 无残留未回填的 Open Questions，每项决策带来源引用

## 4. SFRS 实现（Python + SQLite 常规程序，见 design 决策 9；以机读 schema 为唯一结构依据）

- [x] 4.1 实现 Python 模块骨架与 SQLite 建库初始化：按 2.3 DDL 建库、加载机读 schema 校验器、定义（项目、版本）入口。验证：建库脚本可重复执行（幂等），1.3 样例可经 Python 绑定写入并读回，roundtrip 内容一致
- [x] 4.2 实现结构校验与提交路径：以机读 schema 为权威校验事实集，拒绝时返回可定位失败原因，拒绝不改变仓库状态；SQL 事务保证提交原子生效。验证：pytest 覆盖 1.3 正反样例，行为符合 spec「语义事实集为读写单位」（含"语义报告被拒绝"）与「结构校验及其边界」（含"引用无效被拒绝"）场景
- [x] 4.3 实现增量维护与幂等写入：单实体/关系增量更新、批量提交、失效；单条更新不影响其余实体状态，同内容重复提交幂等。验证：pytest 覆盖 spec「增量维护与幂等写入」全部场景
- [x] 4.4 实现版本组织与历史追溯：事实按（项目、版本）持久化，版本由提交给定；同一版本读取结果确定、其它版本提交不影响本版本、同版本同 ID 不同内容判版本冲突；历史项目版本状态可追溯；来源为时点标注、源码不入库。验证：pytest 覆盖 spec「事实不可变与按版本追溯」「版本由调用方给定」「来源标注与源码不入库」全部场景
- [x] 4.5 实现按范围精确查询与关系遍历：按项目/版本/实体/事实类型/关系条件的 SQL 查询，只返回匹配事实及其证据；遍历只返回显式关系边，不推导新事实。验证：pytest 覆盖 spec「按范围精确查询与关系遍历」两场景
- [x] 4.6 按 design 回填结论实现 Skill 专用调用入口（CLI 或进程内接口）与落盘位置，编写使用文档。验证：文档所载用法可实际执行，与实现及 design 回填结论一致

## 5. 集成验证

- [x] 5.1 端到端演练：用 `layered-semantic-facts` 契约查询模式在一个真实项目上产出事实集 → 以（项目、版本）提交入库 → 修改项目后以新版本提交增量变化 → 分别按历史版本与最新版本查询、沿关系遍历。验证：增量提交只影响变更实体，历史版本可追溯取回，查询与遍历结果与提交内容一致
- [x] 5.2 运行 `openspec validate` 确认全部产物有效；对照 spec 8 个 Requirement 逐场景核对实现，确认无"仓库自行判断语义正确性"等越界行为。验证：validate 通过（或 --strict 下无 error 级问题），逐场景核对结论记录在变更目录
