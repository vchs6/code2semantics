# Design

## Context

现状（均已核实落盘）：`layered-semantic-facts` Skill 已交付契约查询与对话派生两种模式，其事实边界、契约格式与输出 schema 由四份参考文件定义（`skills/layered-semantic-facts/references/` 下 `fact-catalog.md`、`contract-format.md`、`output-schema.md`、`report-template.md`），但契约目前只有 Markdown 形态，无机读权威。事实集为一次性会话产物，无持久化层。生产能力调研（`survey-info-acquisition-tools`）尚未执行，fact-catalog 的"生产方式/弱覆盖处理"待回填（见 epic design「Open Questions」）——本设计不依赖它。

依据产物（config 规则：design 只固化有调研支撑的结论，逐条引用）：

- 事实集需求清单（`../../survey-semantic-fact-requirements/research/semantic-fact-requirements.md`，下称"事实清单"）：四层结构（项目→模块→符号→事实）与各层事实类型/字段；证据定位格式"文件:行号范围"。
- fact-catalog（`skills/layered-semantic-facts/references/fact-catalog.md`）：消费方可查询事实的封闭边界。
- contract-format 与 output-schema（同目录）：查询契约与事实集的结构、校验规则（最小化、gaps 与"超出范围"分列）。
- 定稿 proposal（本变更 `proposal.md`）：SFRS 定位、读写契约、版本模型、职责边界——行为需求以其为唯一依据，本设计不重复论证。

## Goals / Non-Goals

**Goals:**

- 先固化契约机读 schema（JSON Schema，语言无关权威），使仓库及后续消费方以机读 schema 为唯一结构依据（spec「结构校验及其边界」）。
- 设计仓库的行为模型（事实集读写/增量维护/按（项目、版本）组织/精确查询）与以语义实体为单位的内部记录模型，逻辑分层沿用既有契约（决策 6）。
- 以本变更内的有限调研回填 Open Questions 后，固化实体存取布局、索引、实体标识格式与落盘形态。

**Non-Goals:**

- 不回填 fact-catalog 生产方式/弱覆盖处理（属 `survey-info-acquisition-tools`）。
- 不修改契约语义；不改 Skill 的提取行为；除 Skill 外不面向其它调用方（proposal「核心定位」）。
- 不实现事实的下游应用（未列入 proposal 职责清单者均不属于存储服务）。

## Decisions

1. **机读 schema 先行（契约消费约定）**：本变更第一个交付物是契约的机读 schema（JSON Schema），忠实转写 contract-format 与 output-schema 现文（含 `facts` 分层、`evidence` 文件:行号范围、`gaps` 与 `out_of_scope` 分列、最小化约束），不新增契约文档外的结构或约束。备选（消费方直接读 Markdown 契约）被否——契约消费约定明确要求避免各消费方转读漂移。
2. **入库校验复用契约校验语义**：目录封闭边界（fact-catalog）与 output-schema 的结构约束即入库校验规则，仓库不另立校验标准；版本冲突、引用有效性检查是该规则在（项目、版本）维度的落点。依据：contract-format「校验规则」1–3 条、output-schema「约束」节、spec `semantic-fact-query`「可提供事实目录前置确定」。
3. **接口单位为语义事实集，物理单位为语义实体（分层共存）**：读写接口的出入单位是符合输出契约的语义事实集（spec「语义事实集为读写单位」）；仓库内部将事实集分解为带稳定标识的实体、属性与关系组织存储（决策 7），增量更新按实体粒度原子生效，该物理组织对读写契约透明。逻辑分层与语义词汇引用事实清单四层结论与 fact-catalog 各层字段，本设计不创设新层级或新字段。依据：事实清单「分层结构（分析结论）」、fact-catalog 各层表格、proposal「主要提供」1/2 与「核心设计原则」2/4。
4. **仓库对事实透明持久**：存取不改写语义内容，不推理、不补全，保证"取回与提交一致"可检验（spec「语义事实集为读写单位」「结构校验及其边界」）。依据：proposal「核心定位」——事实由 Skill 产生，仓库是持久化方，非事实的生产者或解释者。
5. **单层版本轴：版本由调用方给定，仓库不创建版本**：版本轴只有项目版本，且项目版本是 Skill 提交事实时给定的输入维度（被分析项目的时点状态）——仓库不创建、不推进版本，无固化操作；事实按（项目、版本）持久化，同一事实（凭稳定标识跨项目版本追踪，见 Open Question 2）在相邻项目版本间的状态差异即其历史（spec「事实不可变与按版本追溯」「版本由调用方给定」）。同版本内的写入规则：同 ID 同内容幂等、同 ID 不同内容判版本冲突拒绝（spec「结构校验及其边界」）；提交（含批量）为原子生效单元，读写不撕裂由提交原子性保证。被否的备选：仓库显式固化/自动产生版本——仓库自创版本即替调用方做语义决定，越过"存储与语义解释分离"红线；独立事实版本轴——与项目版本对应的事实状态已完整表达事实历史，独立轴是重复语义；独立快照机制——版本标签已承担一致切面职责。版本保留策略（历史版本是否清理、未指明版本时读取返回哪一版）为调研回填后固化的策略项。
6. **查询语义的逻辑视图沿用分层语义事实模型**：SFRS 的查询语义按事实清单四层（项目→模块→符号→事实）组织，语义词汇与封闭边界沿用 fact-catalog，证据定位沿用"文件:行号范围"。备选（另立一套仓库专属本体）被否——Skill 在"提取"与"仓库查询"间需零翻译成本，且四层结构是调研结论而非本设计的创设。依据：事实清单「分层结构（分析结论）」「语义表达中的作用」、fact-catalog 各层表格。
7. **物理视图以语义实体为单位存储**：存储粒度为带稳定标识的实体、属性与关系，分层不参与存储布局；"层级归属"作为实体的分类元数据保留并参与索引，保证逻辑分层视图可从物理存储重建（对应 proposal「结构决策归属」与核心设计原则 2/4）。备选（按整个事实集文档存储）被否——与增量维护（原则 4）冲突，且跨层引用只能表达为嵌套路径，无法按范围查询与关系遍历。
8. **唯一客户：Skill 专用直连（既定事实，非待调研项）**：SFRS 的唯一客户是 `layered-semantic-facts` Skill（proposal「核心定位」已声明）——Skill 以语义事实集为单位提交提取结果、按需取回已存事实（替代重复提取、渲染报告）；衔接方式为 Skill 直连仓库，不存在其它消费方调用路径。推定：单写者起步，无多客户端并发问题；服务形态倾向宿主本地组件而非网络服务。备选（面向任意消费方的通用网络服务）被否——proposal 明确无其它客户，通用化是无当前需求支撑的前置复杂度。
9. **实现形态：Python 程序 + SQLite 存储（常规确定性软件，非代理按文档执行）**：SFRS 的校验、写入、查询与遍历是确定性处理流程，实现为常规程序（Python 编写，SQLite 作为嵌入存储引擎），不由 AI 代理在运行时按文档描述执行——代理执行的校验与查询不具备"精确、可追溯、一致"所需的可重复性。SQLite 满足：嵌入形态（无独立服务进程，契合决策 8 宿主本地组件）、事务支持（原子生效与数据完整性）、单文件落盘（备份/导入导出简单）。依据：契约消费约定"先固化机读 schema 再实现数据结构（Python 绑定等，仅为当前选择）"、proposal「统一接口」实现形态声明。备选（代理按文档执行读写）被否——非确定性；独立数据库服务被否——单写者场景无网络服务需求。SQLite DDL 与数据结构绑定 MUST 以机读 schema 为唯一依据派生（决策 1），语言无关性由 schema 层保持，Python/SQLite 仅为当前实现选择，不反写入数据模型。

## Risks / Trade-offs

- [机读 schema 转写遗漏 Markdown 契约细节] → 转写任务附逐节核对清单（对照 contract-format/output-schema/fact-catalog 三文件），逐节核对结论落盘验收。
- [契约仅由单一消费方固化，可能与后续消费方需求冲突] → schema 忠实转写、不新增约束；发现契约本身需变更时另行提案，不在本变更中顺手改契约。
- [仓库依赖机读 schema，而 schema 依赖契约现文稳定] → epic 已完成、契约参考文件已定稿；若生产能力调研回填导致契约结构变化，需同步评审本变更的 schema 任务（tasks 中设前置核对项）。
- [实体稳定标识依赖 Skill 提交质量] → 红线已定（身份判定责任在 Skill 提取流程，仓库只校验同 ID 结构一致性）；同 ID 不同内容在同一（项目、版本）内被冲突检查拦截，跨版本漂移记为 Skill 侧责任。
- [有限调研止损后仍有未决项] → 按"调研有度"规则记差距落盘，未决项在实现中采用最保守可选方案并显式标注，不静默假设。

## Migration Plan

纯新增：机读 schema 与仓库实现均为新增文件，不改既有文件；回滚 = 删除新增文件，无数据迁移。仓库自身的落盘位置在 Open Questions 回填后于实现前确定。

## Open Questions

（回填于 2026-10-24 任务 3.2，逐项引用调研纪要 `research/storage-survey.md`；未决项按最保守可选方案固化并标注。）

1. **存储布局与索引结构**（已回填）：三表实体粒度布局（entities/attributes/relations），属性为 EAV 行；覆盖索引 (project, version, fact_type, entity_id) 与 (project, version, name, value, entity_id) 模式；关系表双向索引支撑遍历；`CREATE TABLE IF NOT EXISTS` 幂等建库；多属性 AND 用 INTERSECT。依据：纪要 OQ1（GraphQLite schema 参考、SQLite EAV 实践）。
2. **实体稳定标识机制**（已回填，红线不变）：身份判定责任由 Skill 提取流程承担，仓库不自行推导身份；回填前以 `(事实类型:文件:行号范围)` 作确定性占位标识（保守方案，显式标注待 Skill 侧回填）；仓库仅校验同 ID 结构一致性。依据：纪要 OQ2（OmniGraph 标识红线、OrpheusDB 不可变记录）。
3. **版本保留策略与未指明版本语义**（已回填）：历史版本长期保留、不清理（单写者本地场景）；检索接口要求显式版本参数，不设缺省版本语义（编排器总是解析真实版本后调用）。依据：纪要 OQ3（OrpheusDB 版本保留、Schema Versioning 综述）。
4. **仓库数据落盘位置**（已回填）：单文件 SQLite，位置经环境变量 `SFRS_DB_PATH` 指定，缺省 `~/.atomcode/sfrs/facts.db`（独立于项目代码与 Skill 安装包）。依据：纪要 OQ4（SQLite 嵌入单文件形态）。
