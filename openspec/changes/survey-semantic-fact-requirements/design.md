# Design

## Context

本工件由 `openspec instructions design --change survey-semantic-fact-requirements --json` 的模板、规则和已定稿 `proposal.md` 派生。动机见 proposal 的 Why；本设计仅确定如何执行调研和验收，不预设事实分类或分层结论。

本调研承担主变更 `epic-layered-semantic-fact-skill` 的 apply 上游依赖：配置要求主变更开始前完成调研；报告缺失或存在强制重入要求时，按本方法重新生成并验收。规划工件齐备只表示 apply 准入，必须另行检查研究交付。本变更为文档研究，specs 使用 skip_specs，MUST 保留该约束。

## Goals / Non-Goals

**Goals:**

- 将 proposal 的调研要求转为可执行、可验收的生成过程，交付路径保持 `research/semantic-fact-requirements.md`，验收记录为 `research/validation.md`。
- 在同一报告中保留原始问题、事实需求、外部佐证、结构推导与场景反证链，使下游能够定位采用每项语义结论的理由。
- 把机器可检查的存在性、标识引用与覆盖结构交给临时 Python 校验；由认知评审判断需求覆盖、边界与推导是否成立。两类结果分别记录。

**Non-Goals:**

- 本设计不预设层数、层名、顺序、事实类型数、契约字段结构或存储方式；这些未知项只作为调研问题。
- 不读取 Git 中的被删报告或其它旧报告的分层、类型结论，不比较既有分层方案，不以工具能力、目录深度或查询步数决定结构。
- 不修改 proposal/config、其它变更、产品代码、数据库或接口；不执行 commit、push、archive。对下游仅交付通过验收的研究依据。

## Decisions

### D1. 采用由消费者问题向组织结论单向派生的研究顺序

依据：proposal / What Changes 的“需求先行的层级推导”“分层结论与可追溯性”“有界调研与交付”。

先从消费者要理解、定位、解释、追溯的问题与遗漏后果形成 Q 标识的原始问题，再形成 R 标识的事实需求。每条 R MUST 分析主体与边界、观察粒度、聚合与细化、独立属性/行为、横向关系及证据要求；然后归纳 F 标识的事实类型及语义词汇/字段描述，最后推导层次或其它组织方式。编号仅用于追踪，数量和内容由执行时分析产生，不代表事实类型或层次数的预设。

报告按下列章节交付（章节是研究记录组织，不是软件语义分层）：

1. 目标、范围与方法；
2. 原始消费者问题与遗漏后果；
3. 事实需求与关系分析；
4. 外部佐证及支持边界；
5. 分层推导与边界论证；
6. 事实类型、语义词汇与字段描述；
7. 追踪关系；
8. 典型场景检验；
9. 局限、不确定性与待设计问题。

每个 Q 关联至少一个 R；每个 R 回溯 Q，并指向至少一个 F 和其组织去向；每个 F 解释其保留的语义区别。分析中若发现需要合并或细分，必须回溯问题需求解释，不按既有结构补齐。

被否备选：先画层级再装入需求会把待证结论当输入；完全按文献目录分类会让参考材料替代消费者需求。

### D2. 通过主体、粒度与关系分析推导分层，逐层记录边界决策

依据：proposal / What Changes 的“分析范围与软件单元”“组织关系”“层次与其它维度的职责辨析”“分层结论与可追溯性”。

每个拟定层次记录 L 标识、所回答的 Q、支撑 R/F、主体与粒度、事实覆盖、边界、上下关联、跨层关系和独立理解/查询价值。对每层分别记录为何单列、与相邻粒度合并会损失什么、进一步细分是否有独立需求；未采用的合并/细分是本次需求推导中的备选，不是对旧提案的比较。

分析范围/入口、组织、依赖/交互、证据/知识状态与观察粒度分别建立职责判断，再决定其成为层次、视图、入口或贯穿信息。未作独立层的信息以 O 标识记录去向、关联 R/F 和理由。追踪表 MUST 为 R 提供 L 或 O 去向，允许多对多与跨层关联，不强制唯一父节点、固定深度或经过空层。

尚不确定的边界记录 U 标识、涉及 R、影响、当前能够支持的判断、不能支持的判断与下游处理约束；MUST 仍给出本次证据支持的明确分层结论，不能以“全部待定”替代交付，也不能为填满结构而消除真实不确定性。

被否备选：把目录、项目归属和依赖统一为树会损失重叠及循环；仅列维度而不交付分层结论不能满足 proposal；固定层数会倒置推导顺序。

### D3. 有界核查一手材料，将来源陈述与分析判断分开

依据：proposal / What Changes 的“证据与不确定性”“有界调研与交付”，以及本次重新调研约束。

先完成需求清单初稿及缺口登记，再通过 web 工具核查与具体陈述相关的一手材料（规范、原始文档、论文等）。每个事实条目最多采用两项外部来源；一轮有界核查后未获支持的陈述登记 U 与影响，不不断增补来源或扩张问题域。无须外部佐证的原始需求与分析判断明确标注其性质，不伪装成外部事实。

来源使用 E 标识，记录标题、URL、核查日期、实际支持的窄陈述、定位、相关 R/F、适用限制。来源仅支持被核查陈述，MUST NOT 声称来源规定本报告层数。报告区分原始需求、外部材料支持、分析推导；直接观察、证据推导、语义解释、证据不足、已证实不存在等知识状态须有可区分的表达需求，不能把“未发现”改写为不存在。

被否备选：仅堆砌链接无法复核支持关系；无限搜索不能保证需求覆盖；借用旧报告结论会污染重新推导。

### D4. 用场景检查完整性与分层边界，而不按层数验收

依据：proposal / What Changes 的“典型场景检验”“内部语义与算法”“依赖与交互关系”。

场景以 S 标识记录，至少包括：单项目；同目录多个互不依赖项目；单工作空间多项目及依赖；多工作空间与独立项目混合；跨工作空间依赖；范围外依赖；嵌套项目/工作空间；重叠边界与多工作空间成员；循环依赖；条件成立/不成立/未知的依赖；元素内部控制流与算法；证据不足与已证实不存在的区别。

每个场景给出具体输入假设、消费者问题、预期表达、涉及 R/F/L/O、证据状态、检验结果和遗漏影响。检查整体问题能否追溯到内部行为/计算依据、身份与边界是否保留、物理包含/成员/从属/依赖是否混淆、是否错误扩张范围、是否保留循环及多对多关系、合并是否丢失区别、细分是否制造无需求层次。不适用的检查必须给理由，不以空白或泛称“通过”替代。

被否备选：仅做单项目正常路径不能暴露范围误判；只检查章节存在不能证明分层合理。

### D5. 将交付存在性、引用和覆盖结构固化为可重复校验

依据：proposal / What Changes 的“分层结论与可追溯性”“有界调研与交付”，AGENTS 原则 5、7；不涉及产品实现。

apply 中使用 Python 3 标准库在 `.git/replan-20261025/verify_research.py` 固化本次临时验收器，输入为报告和本变更 tasks；不引入产品依赖。先以缺失报告、悬空标识、无需求支撑的层、R 无组织去向、超出两源和缺少场景的内存夹具验证会失败，再对正式报告运行。输出保留 `.git/replan-20261025/research-content-validation.json`。验收器仅检查存在性、九个章节、Q/R/F/E/L/O/S/U 引用有效性、Q→R→F→L/O 的双向覆盖、每个事实最多两来源以及上述场景覆盖结构；不会自动判断语义论证正确。

报告各实体采用 `### Q1 ...`、`### R1 ...` 等唯一标题；追踪和来源关系采用 Markdown 表格，执行时据本节既定信息项形成最小一致列集，由验收器解析，不由阅读代理记忆维护。无须使用的实体类别可为空，L 必须有明确结论；U 无项时明确写“未发现未决边界”，不可隐藏缺口。

`research/validation.md` MUST 重新写入本次状态，不保留旧验收结论：记录实际命令与退出码、内容校验结果、proposal 各要求到报告章节/任务的对照、场景逐项结论、人工边界评审、残留问题与对下游的限制。记录内嵌可独立保存运行的 Python 校验代码与反例测试，并保存实际 JSON 摘要；本机日志不作为唯一验收依据。OpenSpec strict validate 与 apply 进度只证明规划/追踪状态，必须与报告实存及内容证据联合使用。

被否备选：纯人工逐条数引用不可重复；把 CLI validate 成功当报告完成存在工具盲区；要求自动校验推导真伪会夸大机械检查能力。

## Risks / Trade-offs

- [先前结论污染] → 只使用当前 proposal、配置及本次核查材料；禁止读取已删报告的 Git 内容及旧分层/类型结论。
- [合并过度或细分过度] → 逐层单列/合并/细分论证与场景反证共同验收，不用层数衡量质量。
- [文献核查受限] → 每事实最多两源，止损记录 U；明确影响下游采用的限制，不能声称已完成缺失证据。
- [结构校验通过但语义不完整] → 机械检查与逐条语义评审分别记录；存在未覆盖必需需求时不宣布报告通过。
- [调研结论反向变成预设] → 本 design 的 Open Questions 保持为研究输出问题，报告生成前不填事实类型和层级结构。

## Migration Plan

这是缺失文档的重新生成，不涉及产品部署或数据迁移。按本 design 派生 tasks，经 OpenSpec apply 执行“需求分析→核查与推导→报告产出→验证”，通过后才允许主变更继续消费。规划和研究交付分别验收；阶段状态仅记录在执行日志。执行失败则保留未完成任务与当前证据，不恢复旧报告充当新结果。

## Open Questions

事实分类、词汇和字段的研究回答由报告第 6 节承载，分层及其它组织职责的研究回答由第 5 节承载；方法设计不预置这些答案。可延后到下游设计的问题及影响见报告第 9 节 U1–U5：角色边界、语言语义保真、条件/否定证据、外部佐证与算法证明的限制。
