# 语义事实集需求清单

- **基准日期**：2026-10-22（2026-10-21 首研；同日用户明确指示全面重研，本稿为重研后重新成稿，取代旧稿）
- **定位**：本清单归纳软件项目语言无关的语义表达所需事实，是 epic `epic-layered-semantic-fact-skill` fact-catalog 的蓝本输入。
- **范围**：仅事实需求本身；生产能力判定、契约结构、输出 schema 均不在本清单范围。
- **方法**：从语义表达目标出发收集原始事实需求（事实优先，不从工具输出反推），再按描述对象的聚合度归类定层。层级数量与名称是本调研的分析结论，非预设。重研独立于旧稿重新推导，收敛结论与旧稿的差异在正文标注。

## 原始事实需求与外部佐证

语义表达的目标是：让不读源码的消费者（人或智能体）能回答关于软件项目"是什么、如何组织、有哪些元素、如何互动与运转"的问题。由此收集的原始事实需求，与三个独立外部来源的建模实践相互印证（二手佐证每事实 ≤2 源）：

1. CodeOntology（Java→RDF）：以类表示代码实体（类/方法/构造器/继承层次），可选序列化语句与表达式级事实（来源：CodeOntology, ISWC 2017 论文）。
2. Semantic Code Graph（SCG 信息模型）：节点为代码声明（CLASS/METHOD/PARAM/TYPE 等），边为依赖关系（CALL/EXTEND/OVERRIDE/RETURN_TYPE 等），并要求所有实体与关系均携带源码位置属性（来源：Semantic Code Graph, arXiv:2310.02128）。
3. 遗留系统现代化知识图谱：以可定制的语言无关实体-关系本体建模大型系统（程序、事务、数据表等实体与依赖边、逻辑分组），支撑增量现代化分析（来源：arXiv:2505.06885）。

三者的共同结构：**实体按聚合度分层，关系与行为事实挂接在实体上，且全部带证据定位**。这印证了"先实体分层、后关系/行为事实"的归纳路径，而非预设立场。

## 分层结构（分析结论，重研再收敛）

按描述对象从粗到细的聚合度归类，原始事实需求收敛为四层：

1. **项目层**——描述整个项目的整体语义（它是什么、如何构建与启动、依赖什么）。
2. **模块层**——描述项目的组织单元及其相互关系（划分、职责、依赖、边界）。
3. **符号层**——描述可命名的代码元素（接口、类型、关系、声明的意图）。
4. **事实层**——描述元素之间的互动与约束，以及元素内部做了什么。

与旧稿差异：分层结论**独立再推导后收敛一致**（四层成立，非沿用）；差异在事实类型——项目层新增"构建与运行形态"（旧稿"入口"只覆盖启动点，未覆盖"如何验证它运转"），符号层新增"意图声明"（命名的意图只经由文档注释这一语言无关通道存在，旧稿遗漏），事实层按"跨元素关系 / 元素内部行为"重组呈现（两类事实的证据定位与查询粒度不同，混排会掩盖这一差别）。

## 语义表达中的作用

四层结构对应四类语义表达诉求，缺一则表达不完整：

- **项目层**回答"这是什么系统、如何构建运转与验证"——支撑系统级理解与迁移的整体把握（外部佐证：现代化知识图谱以应用级实体与逻辑分组为分析起点）；
- **模块层**回答"如何组织、边界在哪"——支撑架构理解与模块级变更影响面判断（佐证：现代化知识图谱按逻辑边界做增量分析）；
- **符号层**回答"有哪些可复用/可引用的代码元素、声明了什么意图"——支撑跨语言等价接口的识别（佐证：CodeOntology 以实体类与层次关系为核心；SCG 以声明节点+可见性/修饰符为模型基础）；
- **事实层**回答"元素之间如何互动、有何约束，以及元素内部做了什么"——支撑行为语义的还原（调用链、数据流、错误契约）与迁移的行为等价性判断（元素实现语义）（佐证：SCG 的 CALL/EXTEND 等依赖边；CodeOntology 的语句/表达式级可选序列化）。

自顶向下的聚合关系保证了"最小化"可判定：任何一层事实都可独立满足查询，也可按需向下钻取；下层事实以证据定位挂接回上层元素，形成可溯源的分层事实集。

## 越界自查（重研 2026-10-22）

对照 proposal/design 边界逐项检查：本清单不含任何生产能力判定（未声称任何事实类型可由何工具生产，fact-catalog 的"生产方式待回填"边界保持不变）；不含契约结构定义（未定义查询契约 JSON 字段或输出 schema，"使用契约"仅为事实类型的语义描述）；层级为调研推导结论并保留论证，未预设。结论：无越界内容。
