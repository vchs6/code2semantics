## 1. 目标与边界

消费者应能在用户指定范围内回答：分析了什么、有哪些软件单元、如何组织、彼此依赖及交互什么、如何运行、元素内部如何实现，以及这些回答在何种证据和条件下成立。

用户目录是观察范围，不是自动认定的项目根或工作空间根。范围可含多独立项目、多工作空间及混合集合；物理嵌套、逻辑从属、工作空间成员和依赖是四种不同问题。范围外引用应被保留，引用本身不授权继续分析外部源码。所有“整体”结论均限定在实际观察边界与快照内，不能把范围内的集合自动命名为一个软件产品。

语言无关不等于抹去影响行为的语言特性。例如整数溢出、所有权转移、异常终止、并发顺序要用中立含义保留；源码语法和生态名称可以作为证据，不作为所有语言必须具备的事实类别。源码没有类或模块关键字，也可以具有类型、职责单元、闭包或行为片段；确实不适用时记录理由。

## 2. 方法、来源与止损边界

1. 根据 proposal 的覆盖目标，一次列出 §3 的原始问题集合；不以旧四层或生产工具可输出字段作为入口。

## 4. 事实需求清单、语义词汇与必要信息

下列所有条目均关联主体身份、适用快照/条件和 §6 的证据要求。“未知”可以是合法知识状态，但不能以缺值冒充已知完整；不适用也须说明理由。必要信息按语义列出，不规定字段拼写、序列化和必填规则的实现。

### 4.1 观察边界与软件身份

| ID / 事实类型 | 中立语义词汇 | 必要信息与适用边界 |
|---|---|---|
| F01 分析范围 | 观察范围、包含、排除、授权边界 | 用户指定根和选择规则、实际检查对象、排除对象及理由、外部引用处理边界；根目录不自动生成项目身份 |
| F02 快照与成立上下文 | 版本、快照、配置、生效条件 | 版本或内容依据、未提交差异、配置/平台/特性条件、观察时间；多仓库可各有版本，不凭一个根提交代表全部 |
| F03 软件单元身份 | 主体、别名、定位、候选同一性 | 名称、单元种类、来源命名域、版本/快照、位置及别名、身份依据；同名不是同主体，同路径不同版本也不能直接合并 |
| F04 工作空间语义边界 | 成员集合、管理上下文、工作空间种类 | 工作空间标识、定义位置、语义种类（构建/编辑/联合管理等）、成员规则和排除条件；无工作空间也是允许情形 |
| F05 项目语义边界 | 项目、边界、产物、自主性 | 识别依据、源范围、主要用途/产物、配置入口、候选边界与歧义；项目与生态 package/模块不是普适一一对应，不以“能单独构建”作为唯一判断 |

单元身份应与观察范围、物理路径解耦，但如何生成稳定 ID 留给设计。一个项目可以被多个编辑或管理工作空间引用；具体构建生态可能限制成员归属，这一限制只能附在对应工作空间种类和上下文上。嵌套目录内发现清单是边界证据，不足以直接判定独立项目。

### 4.2 组织关系

| ID / 事实类型 | 中立语义词汇 | 必要信息与适用边界 |
|---|---|---|
| F06 物理包含 | 位于、包含、路径重叠、别名位置 | 路径主体与客体、相对位置、快照和重叠依据；若有链接/映射保留区别；物理路径循环不转化成软件组成循环 |
| F07 工作空间成员 | 属于集合、被排除、成员角色 | 工作空间与成员的身份、直接/规则推导成员、声明来源、条件/角色；多对多关系不能用一个父指针替代 |
| F08 逻辑从属 | 归属、负责、共享分组 | 两端主体、分组目的、语义种类、条件与判断依据；架构或领域分组允许重叠，不宣称逻辑分组等于物理包含 |
| F09 内部组成与出口 | 组成、子系统、部件、暴露 | 整体与部分、组成角色、接口出口、共享组成、适用视角；区分直接组成和推导可达，不把依赖端点放进组成清单 |

判别反例：目录 D 包含项目 A/B，只支持 F06；工作空间 W 列 A/B，支持 F07；A 调用 B 才有相应 F17/F18；A/B 共同属于“支付域”可形成 F08。上述任一事实都不能无条件推导其余事实。直接依赖也不等于组织从属。

### 4.3 对象自身的用途、结构与声明

| ID / 事实类型 | 中立语义词汇 | 必要信息与适用边界 |
|---|---|---|
| F10 用途与领域 | 目标、能力、领域概念、运行形态 | 主体用途、提供能力、领域词汇、库/服务/应用等形态及依据；允许多用途，作者声明与分析解释分开 |
| F11 构建、运行与验证形态 | 输入、产物、入口、启动、部署、验证 | 构建输入与产物、启动点、运行环境、部署单元、测试/验证入口及条件；命令是证据或描述，不代表本次执行成功 |
| F12 配置与条件 | 参数、缺省、覆盖、生效范围 | 配置含义、取值约束、缺省/覆盖关系、影响对象及条件；未知环境值不能被擅自填写 |
| F13 架构职责 | 职责、边界、提供能力、协作 | 组件/模块/子系统职责、边界理由、可见入口、协作对象；物理目录可作证据，但不自动等于一个职责单元 |
| F14 接口与可达性 | 输入、输出、可见、暴露、别名 | 参数与返回语义、可见性、公开可达路径、版本与条件、重导出/别名；声明公开不保证可从目标入口到达 |
| F15 类型与符号结构 | 值域、结构、约束、继承、实现、组合 | 类型及成员的语义、关系两端、泛化/实现/组合类别、表示与行为相关限制；保留溢出、空值、编码等有语义影响的差异 |
| F16 意图和约定声明 | 声明意图、术语、承诺、说明 | 文档/注释/说明来源、关联主体、原意和解释区别、适用版本；意图来源不限 doc 注释，实际行为相悖时保留冲突 |

### 4.4 依赖、调用及跨单元交互

| ID / 事实类型 | 中立语义词汇 | 必要信息与适用边界 |
|---|---|---|
| F17 依赖关系 | 依赖方、被依赖方、条件、阶段、直接性 | 两端身份或未解析目标、依赖种类、方向、用途、声明/解析/观察状态、成立条件、版本约束/实际版本、项目/工作空间/范围边界、证据；构建、代码接口、运行、数据、部署应能区分 |
| F18 调用与派发 | 调用、回调、候选目标、实际发生 | 调用者、调用点、被调用者或候选集合、派发/触发条件、可能/必然/本次已观察的区别；符号引用不是调用证据 |
| F19 数据与消息交互 | 产生、消费、传递、读写、事件 | 数据/消息对象、生产者/消费者、通道或共享介质、方向、格式含义、读写/顺序/事务条件；共同访问数据并不必然互相直接调用 |
| F20 运行与部署协作 | 使用服务、部署前提、资源绑定 | 服务/部署单元、提供与使用角色、端点/资源、启动/可用性条件及交互证据；网络地址不同不能单独证明不同逻辑服务 |
| F21 依赖路径与循环 | 路径、可达、环、条件共存 | 有序路径、各直接边引用、关系种类、配置组合、环中主体、联合条件能否满足；原始边保留，不把环折叠摘要当原始项目 |

关系的方向按语义定义：A 依赖 B 记“依赖方 A → 被依赖方 B”；数据流可从生产者 B → 消费者 A，不能因为流向相反而改写依赖方向。同一主体对可以有多条不同类型、条件和版本的关系。

跨项目、跨工作空间和范围外是关系的边界属性，不是互斥依赖类型。外部目标只知道名称/版本声明时保留外部引用及解析未知，不编造其内部接口和算法。记录 W1/A → W2/B 不能由成员关系自动推导所有 W1 项目依赖所有 W2 项目。

声明依赖、解析生效和运行观测属于不同断言。传递依赖必须能回溯直接边；混合“构建→调用→数据”路径如需表达，必须保留每一段语义，不擅自把它概括为同一种传递关系。

循环不能丢边以迁就层次。A → B → A 只有在指定种类和联合条件可满足时才是该上下文中的环；如果两边分别仅在互斥平台成立，应记为“合并视图有候选环，单配置未证实环”。环也不等于一定发生死锁或不能构建；是否非法由生态或行为约束另行说明。

### 4.5 状态、约束和代码级算法

| ID / 事实类型 | 中立语义词汇 | 必要信息与适用边界 |
|---|---|---|
| F22 状态与资源生命周期 | 初始状态、迁移、获取、转移、释放 | 状态/资源主体、触发、前后状态、所有权/别名、合法序列、创建/释放顺序、失败后状态；资源不是只有内存 |

## 5. 从需求到层级的推导及语义表达中的作用

### 5.1 推导过程

首先，R01/R02 要求一个导航入口能描述“本次观察集合里有哪些单元”，而不能先断定有一个总项目。R03 又表明工作空间成员、物理包含和逻辑从属可能交叠，因此集合视图不能成为所有关系的唯一父节点。

其次，R04 的用途与运行问题以项目/软件整体为主体；R03/R04 的职责分解以组件、模块、子系统等逻辑组成单元为主体；R05 的接口与类型以可引用声明为主体；R09—R12 则要求进入声明内部的状态转换、控制路径和算法片段。按这些问题的观察粒度，归纳出下面五种导航视图。数字是本轮归纳结果，不是语言生态或本体必须采用的固定层数。

| 导航视图（从整体到细节） | 聚合对象与要回答的问题 | 主要依据与作用 |
|---|---|---|
| V1 联合范围与组织视图 | 本次看了哪些独立项目/工作空间，集合如何重叠？ | R01—R03、F01—F09；保证多单元入口不被冒充为单项目 |
| V2 项目整体视图 | 单个项目为何存在、如何构建运行，依赖谁？ | R04/R06、F10—F12、F17/F20；支撑整体语义与外部边界理解 |
| V3 逻辑组成视图 | 职责如何分解、模块/组件如何协作？ | R03/R04、F08/F09/F13；支撑架构解释，可有多级组成和重叠分组 |
| V4 声明与接口视图 | 有哪些类型、符号、可达接口和使用承诺？ | R05/R11、F14—F16/F25；支撑精确引用与接口含义 |
| V5 实现行为视图 | 内部路径如何转换数据、状态和错误并实现算法？ | R07/R09—R12、F18/F22—F28；支撑代码级语义解释和边界追踪 |

这是一种需求导航层次，不要求每个对象经过恰好五级，也不强制为缺失的工作空间/模块/声明制造占位实体。脚本可从项目直接深入行为片段；复杂组件可有多个子层。工作空间不是所有项目的必经祖先，联合范围也不是新造的软件工程实体。

第三，F17—F21、F06—F09 之类事实连接一个或多个视图的主体，它们形成横向或跨层关系视角；F29—F32 贯穿所有视图。每一种主体上的描述都是“事实”，因此不再把“事实”当成符号下唯一的一层。关系需要逻辑可查询和保留，但本报告没有据此选择树、图或关系表作为物理存储。

### 5.2 备选方式与取舍

- **旧四层（项目→模块→符号→事实）**：项目入口无法容纳没有总项目的联合范围；“事实”把关系、证据和内部算法混为末层。故本轮不直接沿用。
- **在旧四层上增加工作空间总根**：可以展示部分集合，却错误要求每个项目有唯一工作空间，且循环和跨范围关系仍无合理位置。故不采用唯一祖先链。
- **完全平铺所有主体和关系**：能保留拓扑，但缺少从整体到局部的理解路线，不满足逐步深入的目标。故以五种导航视图组织认知，再独立表达关系及证据。
- **严格固定五层树**：虽然名字与本稿相似，仍会制造空层并破坏多成员/重叠结构。故明确拒绝这一解释。

五种视图是报告组织结论；最终 catalog 的层级命名、编码、查询投影和输出形态仍须由 epic 据此设计。不能把“五视图”直接视为新的产品枚举已经生效。

## 6. 证据、不确定性与否定结论

事实内容、来源性质与知识状态是独立维度，不能用一个“可信/不可信”值替代。

| 情形 | 可支持的断言 | 不能升级为 |
|---|---|---|
| 直接观察到清单声明 A 依赖 B | 在该快照/位置直接观察到“声明依赖” | 所有配置均生效，或本次运行实际调用 |
| 在给定条件按成员规则推导出 P 属 W | 保留规则、前提和条件的证据推导 | 不带条件的生态通则 |
| 从实现和说明解释“采用二分查找” | 有定位和假设的语义解释 | 算法正确性或复杂度已证明 |
| 找不到 B 的源码/动态目标不明 | 外部或未解析引用、候选目标与缺口 | B 不存在或 A 没有该依赖 |
| 完整检查限定集合后无某种声明 | 在给定快照/配置/谓词下已证实不存在该声明 | 不存在运行、数据、部署等其他依赖 |
| 文档说无副作用但实现写日志 | 两项断言及各自定位并存，标明冲突 | 默选文档或实现摘要删除另一项 |

“直接观察”说明证据的取得方式，不保证证据内容就是运行真相；观察到作者声明依然是声明事实。推导和语义解释的区别是后者包含解释性判断，两者都需可追溯依据。证据不足、解析失败、不适用、未检查与零结果不能混用。

负面断言至少说明：否定哪个主体对/集合、哪种关系、哪个方向、哪份快照、哪组配置、检查了哪些载体、是否封闭完整、残留盲区。例如“快照 k 的两个清单在配置 c 中没有声明相互构建依赖”，并不证明它们运行时无 RPC。循环结论同样受此覆盖边界限制。

同名实体、多版本、路径别名和冲突证据不应自动合并。关系跨越两个仓库时两端分别记录快照；仅有一端源码证据可支持该端的声明，不能替另一端作履约保证。

## 7. 从整体深入代码级算法的见证

以下是说明表达充分性的假想算法，不是本仓库的真实源码或实测结果。

项目 P 提供“在有序序列中寻找首个不小于阈值的位置”的接口 search。其职责组件 C 暴露元素 f，f 内部以半开区间 [lo, hi) 迭代：

- 输入域是有序序列；返回位置 i 满足此前元素都小于阈值，i 等于长度表示不存在符合元素；空序列返回 0（F14/F25）。
- 初始 lo=0、hi=长度；循环条件 lo<hi；中点由 lo 与 hi 差值确定；当中点元素小于阈值时 lo=mid+1，否则 hi=mid；lo=hi 时返回 lo（F26/F27）。
- 候选不变量为 0≤lo≤hi≤长度，区间外两侧已完成排除；每步区间缩小是终止论证线索，数学正确性仍需独立证明（F28/F30）。
- 若源实现以可能溢出的求和计算中点，则记录数值条件及风险，不能用一句“二分查找”掩盖源行为；比较回调抛错、写状态或顺序不稳定也分别进入 F18/F22—F25。
- “对数次比较”需以区间缩小与比较代价假设为据；没有测量就不填写耗时/内存数值（F28）。
- 一条事实定位到输入承诺，另一条定位到循环和更新；作者注释、实现解释和测试观测各自保留，缺失证据明确标未知（F29—F32）。

导航可以从 V2 的项目能力，经 V3 组件职责、V4 接口，深入 V5 片段，再回查 V1 的项目/工作空间归属。任何一步的横向调用可以跨项目，算法片段无需被复制为对方项目的组成。

该例同时说明：本需求不仅要求控制流形状，还需要输入域、计算规则、不变量、边界行为、错误和证据；也不强迫把语法写法、临时变量名直接作为中立事实。

## 8. 典型场景检验

### 8.3 场景检查结论与反断言

S01—S10 五个维度均有表达见证。关键反断言包括：共同目录不等于同项目；成员不等于依赖；依赖不等于组成；可能调用不等于实际调用；外部引用不扩大范围；合并条件视图的环不必在任一配置成立；未发现不等于不存在；共享主体不必唯一归属；语言无关不删除影响行为的细节。

这些是需求清单的表达充分性检查，不能提升为源码正确性证明、真实依赖枚举完整性或生产能力测评。

新增或显式补足重点：范围/快照、软件身份、工作空间语义、成员多对多、物理与逻辑区别、条件及外部依赖、部署协作、可追溯循环、证据推导与覆盖/冲突/否定边界。

对下游的直接交接：

1. **fact-catalog**：现有文件仍为旧四层、20 类及具体字段。需要逐条消费 F01—F32，明确层级视图、关系归属、术语和适用性；不能直接把本报告词汇当新增可查询字段。
2. **contract-format / output-schema**：需在 catalog 定稿后处理多范围/多单元身份、关系主体客体、版本配置、外部引用、覆盖与未知的表达；本报告不决定其字段拼写或协议版本。
3. **survey-info-acquisition-tools**：其报告明示输入旧 20 类，原能力结论不能继承到新集合；由 epic 据 catalog 提出新的能力调研要求。
4. **构造、查询、仓库与验证消费者**：需要评估既有“文件:行范围”证据对清单/文档/运行记录、身份与多快照、关系和知识状态的适配。不能因本报告交付就宣称这些实现已支持。

本轮不改写下游封闭 catalog，避免在没有相应契约设计和实现验证的情况下误扩大产品能力。历史 tasks 的同步记录属于 2026-10-22 轮次，不作为本轮已同步的主张。

## 10. 局限、差距与待设计问题

- 本报告是有界需求清单，不证明对所有语言、架构和程序都穷尽。形式验证、安全性质、分布式一致性等深入事实可由实际需求触发专门研究，当前已保留约束/证据表达入口。
- 没有对真实多工作空间或循环源码样本运行工具；§8 的通过只表示概念上可表达。是否能被生产、精度与成本如何，属于后续能力研究和非空测试。
- 工作空间/项目的生态映射不是普适一对一；明确识别依据但不决定自动发现算法。身份生成、重命名/版本关联、路径别名消歧需设计，存在歧义不能先强行合并。
- 否定断言要求封闭覆盖；动态加载、外部配置、反射、网络依赖等使完整否定往往不可得。此时记录未知和盲区，不因为表达需求存在就保证能够证明不存在。
- 复杂度、算法意图和终止主张需相应论证；本轮不提供通用正确性证明算法，不把自然语言解释当实证。
- 概念关系需要被保留并可按语义区分，但关系的持久化、查询遍历、循环展示/摘要、投影及增量失效策略留给实现设计，不指定数据库或序列化格式。
- 外部官方文档是访问日快照的实例佐证；本轮不遍历生态所有版本。若将来发现来源变化，应追溯受影响需求，不能悄然修改已验证结论。
- 后续设计顺序维持 fact-catalog → contract-format → output-schema；新一轮目录补录通过其治理机制，需回溯本报告需求及差异。
